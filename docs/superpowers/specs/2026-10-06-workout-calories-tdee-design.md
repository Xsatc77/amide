# Workout calorie estimates, TDEE and the burn chart: design

Date: 2026-10-06. Status: awaiting review.

## Goal

When someone logs a workout, Amide estimates the calories burned automatically, using the owner's exercise
workbook (230 exercises, MET values, default seconds per rep and rest). The workout and its calories show in that
day's Journal entry. A new Energy tab on the Workouts page shows a full TDEE breakdown and a chart of estimated
workout burn against TDEE.

## What the owner said

- The workbook's model is the model: MET x 3.5 x kg / 200 x minutes, active time from sets x reps x seconds per rep,
  rest from the workbook's rest column. "Rest is good to go": its default rest per set is used as is.
- The Journal page (the Journal tab of the Measurements page) gets a **Log Workout** button; the logged workout also
  appears in that Journal entry.
- Plan exercises are matched to workbook exercises by fuzzy logic, by function. Exercises can also be added on the
  day, and then the user must enter what the calculation needs.
- **The user logs exact sets and exact reps, never a range.** A plan's "8-12" is only a display; the log form needs a
  whole number of reps per set.
- TDEE: reproduce the data at tdeecalculator.org exactly. Chart: daily stacked bars, TDEE baseline plus the workout's
  net kcal, with the goal target as a line.
- The exercise database ships in the repo (it is the owner's own work, derived from the public Compendium of
  Physical Activities). No vendor or price-list data is involved anywhere in this feature.

## Out of scope

- A workout with no plan (a plan day is always chosen); reading the xlsx at runtime (the app uses a generated JSON
  file); the site's imperial/metric toggle (Amide is imperial).
- The workbook's Treadmill Jog and Treadmill Run carry MET 3.5, the same as walking. They load as they are; the
  owner can edit the workbook and regenerate. Flagged to the owner, not changed.

## 1. Exercise data

`app/workouts/exercise_data.json`, generated by `tools/build_exercise_data.py` from the workbook with the standard
library only (xlsx is a zip of XML; no new dependency). Contents:

- `exercises`: name, equipment, primary area, movement pattern, compendium code, MET, evidence type
  ("Direct Compendium activity" or "Mapped estimate"), default style, seconds per rep, default rest per set in
  minutes, calorie model ("rep" or "duration"), note.
- `aliases`: alias to canonical exercise (516 rows).
- `styles`: the seven style profiles (MET, seconds per rep, rest per set), for the style override.
- `compendium`: the source codes and MET values.

`app/workouts/exercise_db.py` loads it once and offers `get(name)`, `search(text)` and `names()`. A test checks the
file against the workbook's published counts (230 exercises, every alias pointing at a real exercise).

## 2. Calorie engine (`app/workouts/calories.py`, pure)

```
active_min = sets * reps * sec_per_rep / 60              (rep-based)
active_min = minutes entered                              (duration-based)
rest_min   = max(sets - 1, 0) * rest_per_set_min         (rep-based only)
gross_work = MET * 3.5 * kg / 200 * active_min
net_work   = (MET - 1) * 3.5 * kg / 200 * active_min
gross_rest = 1.5 * 3.5 * kg / 200 * rest_min
net_rest   = 0.5 * 3.5 * kg / 200 * rest_min
gross      = gross_work + gross_rest      net = net_work + net_rest
volume_lb  = load * implements * reps * sets
kg         = lb / 2.2046226218
```

Returns a frozen dataclass. Missing or non-positive inputs give `None`, never a guess. The workbook's two
calculators agree with these formulas; tests use hand-worked cases (for example a barbell bench press at 185 lb,
4 x 8, body weight 200 lb).

## 3. Matching plan exercises to the database (`app/workouts/exercise_match.py`)

Tiers, first hit wins: exact name; alias (case and punctuation insensitive); normalised name (reusing
`app.library.matching.name_key` style normalisation, plus abbreviations such as DB, BB, KB, BW); then a fuzzy tier
scoring token overlap and difflib similarity, with a bonus for the same equipment and movement words. A fuzzy hit
below a confidence threshold is returned as a **suggestion**, not a match.

`WorkoutExercise` gains `db_exercise` (the canonical name, nullable) and `db_exercise_confirmed` (bool). A plan
save matches every exercise automatically; a confident match is stored, a suggestion is shown on the plan editor as
"closest: X" with a one-click confirm and a search box to choose another. Unmatched exercises log normally and show
no calories, with the reason.

## 4. Logging

Data model (migration 0034):

- `workout_exercises`: `db_exercise` (String 200, null), `db_exercise_confirmed` (Boolean, default false).
- `workout_exercise_logs`: `exercise_id` becomes nullable (an exercise added on the day has no plan row); new columns
  `name` (String 200, the name as logged), `db_exercise` (String 200, null), `sets` (Integer), `duration_min`
  (Float), `implements` (Integer, default 1), `style` (String 40), `sec_per_rep` (Float), `rest_min` (Float),
  `met` (Float), `body_weight_lb` (Float), `gross_kcal`, `net_kcal`, `volume_lb` (Float, all null when not
  calculable). Everything the estimate used is stored, so a later change to the database never rewrites history.

Log form (`/workouts/day/{id}/log`, extended): each plan exercise row has Done, load and unit (as now), plus **Sets**
and **Reps per set**, both whole numbers. A plan's "3" sets pre-fills Sets; a rep range pre-fills nothing, so the
user types the real number. A row that is ticked Done with a matched exercise needs sets and reps (or minutes for
a duration exercise) before it calculates; if they are missing the row saves and shows "enter sets and reps for a
calorie estimate". Reps and sets are validated as whole numbers 1-999; load as a non-negative finite number.
"+ Add exercise" adds rows with a search box over the database, and the same fields. A body-weight field (lb,
pre-filled from the latest weigh-in, editable) applies to the whole log; with none, no calories are calculated and
the page says why. A style selector (default from the database) is available per row under "Adjust".

Saving still replaces the day's log for that date (existing behaviour) and recalculates. Loads in kg convert to lb
for volume only; calories never use the load.

## 5. Journal

The Journal tab gets a **Log Workout** button beside New Entry. It opens a small dialog: choose a plan day (active
plan days, today's first) and a date, then continue to the log form. Each Journal entry's workout line becomes
"Push Day, 5/6 done, about 310 kcal (net)". The same line is used for shared entries, because workouts are already
part of the shared personal-data view.

## 6. TDEE (`app/measurements/tdee.py`, pure) and the Energy tab

Reproduces the site's outputs for sex, age, height, weight, activity level and life stage:

- BMR: Mifflin-St Jeor; Harris-Benedict (revised, Roza and Shizgal); Katch-McArdle and Cunningham from lean body
  mass (Boer formula); the average of the four.
- TDEE = BMR x activity factor (1.2, 1.375, 1.55, 1.725, 1.9, the levels Amide already has); "adjusted" TDEE applies
  the life-stage rule; TDEE at every activity level (shown as a bar chart with the current level highlighted).
- Split: BMR, activity (TDEE - BMR - food digestion) and thermic effect of food (10% of TDEE), with percentages.
- BMI and its category; lean body mass in kg and lb; minimum daily calories (the safety floor); waist-to-height ratio,
  fat body mass and maximum fat metabolism when body fat percent is known (Amide already derives it from tape
  measurements); the "math" lines.
- Goal ladder: aggressive cut -1000, faster cut -750, cut -500, maintain, lean gain +250, bulk +500.
- Macro grid: cut / maintain / bulk against low / moderate / high carb, with the protein/carb/fat split, grams and
  grams per meal for the selected cell.
- Life stage (women, optional, a new profile field): luteal +150; pregnancy trimesters +0, +340, +452;
  breastfeeding +400 with a 1,800 floor; perimenopause -175; PCOS -6% of BMR.

Because the numbers must match the site, the tests include profiles whose expected values were read from the site's
own calculator (numbers only). The Energy tab reads profile and latest weight like the Macros tab does and shows the
same "complete your profile" prompt when a field is missing. The Macros tab keeps working as it does today.

## 7. Chart

Pure geometry in `app/workouts/burn_chart.py`, rendered as inline SVG (no browser storage, no new dependency): one
bar per day over 7, 30 or 90 days. Each bar stacks the TDEE baseline (colored by its BMR / activity / food parts)
with that day's logged net workout kcal on top in the accent color; a dashed line marks the goal target
(TDEE plus the owner's macro goal). Hover shows the day, TDEE, workout kcal and percent of TDEE. The axis fits the
data with margin, like the price chart. A note under the chart says TDEE already includes typical exercise, so the
stack compares the day's logged workout to the baseline and is not a strict total. Days with no workout show the
baseline only. Without a profile or weight the chart explains what is missing instead of drawing.

## Testing

Formula tests (hand-worked from the workbook), exercise-data integrity, matcher tiers with invented and real
exercise names (names of gym exercises are not private data), form validation (non-integer reps, missing sets,
missing weight, ticked-but-blank), snapshot immutability, Journal rendering and sharing, the Log Workout dialog,
TDEE against the site's values, chart geometry, and migration upgrade/downgrade. The browser is used to check the
dialog, the log form and both charts at desktop and phone width and in dark theme. An independent reviewer checks
the finished branch.

## Risks

- Matching is heuristic; wrong silent matches would mislead, so only confident matches are stored and the rest ask.
- Mapped METs are estimates (the workbook says so); the UI labels every estimate "estimated" and shows the evidence
  type in the exercise detail.
- Alembic must keep a single head; the migration is additive, nullable-first, with a downgrade.
